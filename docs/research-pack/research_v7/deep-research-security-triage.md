# Primary-source triage of the deep-research security claims

Date: 2026-10-22. Input: `research_v7/deep-research-report.md`, treated as unverified research leads. Scope: its FFmpeg version, RTSP/HLS advisory and proposed network/probe mitigation claims. No application, FFmpeg media operation, exploit reproduction or GPU workload was run.

## Decision

**Reject the report's headline that both the RTSP whitelist bypass and redirect loop remain unfixed in the pinned FFmpeg 9.0.2. They are different issues.** The exact selected source contains the RTSP scheme-validation fix and the HLS child-playlist fix. It still contains an RTSP reconnect-to-redirect loop without a redirect counter. That remaining issue matters to an explicitly admitted live RTSP route; it does not reopen RTSP access in the selected ordinary `fd`-only file probe or turn the Rust HTTP(S) materialization route into RTSP.

Keep the exact 9.0.2 research/profile baseline for the existing offline/materialized-input design. Do not downgrade it to 8.1.3 or add already-present fixes again. **Do not qualify or publish direct FFmpeg RTSP input support using the unchanged 9.0.2 profile.** That route remains unavailable until its component lock selects an exact corrected upstream commit or reviewed backport and CI qualifies bounded redirects, destination authorization and cancellation. If RTSP is a required initial coverage row, its unresolved route blocks that row and the release gate; it cannot be silently removed from required scope. This audit does not identify a newer safe release number and therefore does not invent one.

## Narrow consequences for the current design

1. **Keep the source-level distinction in component qualification.** Record the scheme fix and HLS child-open fix as present at the exact pin, and the RTSP redirect-count issue as unresolved for direct live RTSP. The corresponding source and component lock must identify any later selected correction; a generic “9.x” or scanner pass cannot resolve it. Existing CI security canaries should exercise the packaged component, but this document makes no claim those tests have already passed.

2. **Keep ordinary files and downloaded sources on their selected routes.** Ordinary probes use a seekable already-open `fd:` input, an explicit `fd`-only protocol list, fixed demuxer/options and no hidden network authorization. HLS/DASH dependencies are resolved under the existing typed resolver and grant policy. Downloadable HTTP(S) sources pass through the Rust ingester, which owns each redirect's destination/credentials and finite redirect/time/size limits before offline probing. A broad `--allow-network` flag is not an adequate replacement for that policy.

3. **Do not pretend a wrapper counter controls redirects hidden inside FFmpeg.** The current subprocess interface does not give the wrapper a pre-connect callback for every RTSP redirect. A wall-clock supervisor can bound the job's lifetime and cancel it, but cannot prove an internal redirect-count or destination policy. The direct RTSP route therefore needs its own qualified corrected component/route before admission. The scheme fix still does not authorize arbitrary destination hosts, and protocol whitelists alone are not SSRF destination controls. Keep finite capture/deadline and process cleanup even after the redirect-count fix.

This leaves CPU/GPU execution, native/browser presentation and ordinary portable packaging unchanged. No emergency downgrade, new OS sandbox project or application-wide ban on legitimate file inputs follows from the incorrect headline.

## Other security lead retained as unverified

The report also calls an older DASH issue a “CVE-2023-6603 pattern.” The cited [Red Hat record](https://bugzilla.redhat.com/show_bug.cgi?id=2334335) includes a multi-finding historical report; CVE-2023-6603 itself concerns an HLS initialization null dereference, not a verified current DASH whitelist bypass. The official FFmpeg security index associates that CVE with fix `28c83584e8f3cd747c1476a74cc2841d3d1fa7f3`. No new claim that the older DASH behavior survives this pin is accepted here. The typed resolver boundary remains required independently of that historical allegation.

## Preserved primary evidence and limits

`research_v7/security-sources/manifest.json` records source URLs, exact commit, SHA-256, byte/line counts and upstream Git blob identities. Both `ffmpeg-9.0.2-libavformat-rtsp.c` and `ffmpeg-9.0.2-libavformat-hls.c` are **complete source files**. Their locally recomputed Git blob hashes match the upstream returned hashes, so excerpts have not been disguised as complete bodies. The three `commit-*.json` files preserve connector-normalized upstream commit metadata and the returned single-file patches; they are labeled as normalized records rather than raw HTTP responses.

Direct web retrieval of several GitHub/Forgejo pages failed. The official GitHub repository connector subsequently provided the complete pinned source and fix commits. Advisory pages were inspected through web retrieval but are not archived here as full HTML. No exploit sample was executed. Source presence establishes these narrow code facts; actual packaged reachability, bounded behavior and compatibility still require the existing GitHub CI gates.
