# Numera Wiz v6 delivery closure review

**Review date:** 2026-10-22. **Reviewed baseline:** the revision 5 chapter inputs and selected pinned dependency evidence. **Status:** source/document audit; no application, FFmpeg, browser, GPU or CI execution was performed.

This review addresses the delivery path that an implementation agent must complete. The v5 document already has substantial security, component, test and release requirements. The findings below identify where those requirements still leave an observable user outcome or a cross-component transition undefined. They do not invalidate the prior fixes or add a new product family.

## Findings and integration locations

| ID | Priority and affected v5 anchor | Confirmed gap | Required resolution in the main mandate |
|---|---|---|---|
| DC6-01 | P1 — `mandate-delivery.md`, Portable artifacts and platform scope; Security boundaries | Portable extraction and a chosen data root are specified, but the owned directory layout, child temporary/cache environment, interrupted first extraction and repair outcome are not. A helper may still use ambient temporary/cache locations despite the one-EXE promise. | Define the owned layout and child-only environment, staged manifest-checked extraction, disk/permission failure, repair without an in-use profile mutation, and cleanup distinctions. | DC6-02 | P1 — `mandate-architecture.md`, Process and transport ownership; Public API and browser authentication | The owner runtime record includes build identity, but the client compatibility decision is unspecified. An idle bridge is allowed to let the owner exit, yet its next request has no specified restart/recredential behavior. | Exact current-build attachment contract in v1; an incompatible owner is reported without killing its jobs. A bridge reattaches to the same data-root/principal and refreshes transport credentials while preserving the original durable request identity. |
| DC6-03 | P1 — `mandate-delivery.md`, Portable artifacts and platform scope; `mandate-architecture.md`, Commands, durable project state, and save | Updates are called rollback-capable, but there is no transaction spanning the app binary, durable-store schema, unsaved edits, receipts and accepted jobs. Replacing a binary alone cannot undo a destructive schema migration. | Select explicit manual/offline app replacement, a drained owner, versioned durable-store generations, a recoverable activation marker and a precise rollback boundary. | DC6-05 | P2 — `mandate-delivery.md`, FFmpeg component profiles and licensing; `mandate-sequence.md`, E02 | The required component closure is described in prose, but there is no defined release input/output contract tying registry requirements to exact configure results, native imports, source archives and redistribution artifacts. | Introduce a minimal machine-readable profile/build record and per-capability closure output. | DC6-06 | P1 — `mandate-delivery.md`, Required suites and assertions; `mandate-sequence.md`, E01-E10 | The suites are meaningful, but the dependency graph, required completion records and behavior of missing/skipped jobs are left implicit. ## Source observations used for the selected corrections

- Microsoft documents that NTFS supports ACLs while exFAT/FAT32 do not. A writable removable filesystem therefore does not by itself satisfy v5's user-only credential contract. The selected solution is explicit root qualification and a chosen secure data root, not a hidden AppData fallback. [Filesystem comparison](https://learn.microsoft.com/en-us/windows/win32/fileio/filesystem-functionality-comparison)
- Microsoft documents how DLL searches can reach the working directory and PATH. A private extracted FFmpeg profile needs deliberate dependency resolution; hardening a parent process alone is not evidence that a child binary has the same loader behavior. [DLL security](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-security) · [Search order](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-search-order)
- Claude Code documents `${VAR}` expansion in HTTP headers. That supplies one concrete direct-HTTP configuration path; a protected token file is read into the launching process's environment by the setup flow, not automatically dereferenced by generic MCP JSON. Exact client versions still need qualification. [Official MCP setup](https://code.claude.com/docs/en/mcp#environment-variable-expansion-in-mcp-json)
- GitHub documents immutable workflow artifacts and digest validation during download. Its attestation verifier can bind provenance to a repository/workflow and has an offline bundle option. These mechanisms support artifact identity; they do not prove media correctness or that a submitted owner report came from particular hardware. [Artifacts](https://docs.github.com/en/actions/tutorials/store-and-share-data) · [Attestation verification](https://cli.github.com/manual/gh_attestation_verify)
- The archived redb API distinguishes database ownership/open modes and shows explicit transaction commits. A Numera schema migration/rollback protocol is an application responsibility; neither `Cargo.lock` nor a library version alone supplies it. [Pinned source](https://github.com/cberner/redb/blob/v4.4.0/src/db.rs)

## What this review deliberately preserves

The single public executable, local native FFmpeg engine, shared Rust UI, private owner IPC/public loopback separation, scoped principals, publication fences, bounded volatile controls, fixed supported platforms, CPU-only path, qualified-GPU preference, hosted builds/tests and owner-local GPU exception remain unchanged. No new language/runtime installation is added to ordinary use. The changes close bootstrap, maintenance and evidence transitions around that existing design.
